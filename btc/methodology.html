How this was actually built.

The Hashrate Desk is a Bitcoin mining economics model sitting on a Kimball star schema. This page is the working: the grain decisions, the SQL, the data-quality assertions and their results, the tools, and the parts I got wrong on the first pass. Written against the Sr. Data Architect Specialist posting at Samyang America, because a work sample that does not answer the actual requirements is decoration.

02

What built what

Every tool listed here did a job on this project. Where a tool could not do the job I wanted, that is stated rather than papered over.

PG
Supabase, managed Postgres 17
the warehouse. live, not a mockup.

Schema mining_dw: 6 dimensions, 4 fact tables, 3 semantic views. Built with versioned migrations, seeded with real network data and real price provenance, and queried for every figure quoted on this page. The five data-quality assertions in section 05 were executed against it on 16 August 2026 and the results printed here are that run's output.

LC
LucidChart
entity relationship diagram

The ERD in section 03. LucidChart imports a SQL DDL file and generates entities and relationships from it, so the diagram is generated from the same DDL that built the database rather than drawn by hand beside it. That matters: a hand-drawn ERD drifts from the schema within a week.

XL
Google Sheets and Excel
the model, independently reimplemented

A seven-tab workbook holding the same model as live formulas. It exists as a cross-check: two independent implementations of the same arithmetic, one in JavaScript and one in spreadsheet formulas, agreeing to the cent. That caught nothing this time, which is the point of doing it.

JS
Vanilla JavaScript and hand-written SVG
the interface

One self-contained HTML file, no framework, no chart library, no build step. Every chart is SVG generated from the model. The palette was run through a colourblind-separation validator rather than eyeballed, which is why the hardware scatter is capped at three colour categories.

TV
TradingView
display only. read this part.

TradingView has no readable public price API. The widgets are cross-origin iframes by design, so page JavaScript cannot read a number out of one, and scanner.tradingview.com is not a supported endpoint and sends no permissive CORS header. The TradingView widget on the Desk is the on-screen reference. It drives nothing.

$$
Coinbase and Kraken public APIs
the price that drives the arithmetic

Both publish Access-Control-Allow-Origin: *, so a static page can read them. I take both and cross-check: agreement inside 0.5% shows a green badge, wider disagreement raises a warning, and no answer at all falls back to a dated snapshot and says so. A single feed would have been less code and a worse system.

BC
mempool.space, blockchain.info, Hashrate Index
chain state and mining reference

Difficulty, height, hashrate, fee share and hashprice. Difficulty agreed to the decimal across three independent sources, which is the sort of thing worth checking before you build on a number.

Where I would not let a claim stand

I wanted a live TradingView feed driving the model, because that is what futures desks watch. It cannot be done from a static page, and pretending otherwise would fall apart the first time an interviewer opened the network tab. The honest architecture is worse marketing and better engineering: name the display source, name the calculation source, and make the failure mode visible.

03

Conceptual, logical, physical

The posting asks for all three layers. They are genuinely different artifacts and the differences are where the work is.

Conceptual

Five questions, no tables. What does a fleet cost to run. What happens if I swap machine generation. What does the network spend to make one coin. How does profit move when difficulty retargets. Which machine earns most per watt.

Output: a list of questions and the business nouns in them. If you cannot write this down, the schema will be wrong.

Logical

Bus matrix of five processes against conformed dimensions. One grain sentence per fact. Every measure classified additive, semi-additive or non-additive. Keys named but not typed. Platform-independent.

Output: the design you would defend in a review. This is where the retarget grain decision was made and it cost nothing to change here.

Physical

Postgres types, precision on every numeric, primary and foreign keys, CHECK constraints encoding consensus rules, composite key ordering chosen for the access pattern, comments as metadata.

Output: running DDL. Changing the grain here is a migration and a backfill.

The star

The grain sentence, and what it cost to get right

fct_fleet_mining_day: one row per fleet deployment, per UTC day, per difficulty-epoch segment within that day.

The first version did not have that last clause. It was one row per fleet per day, which is the obvious design and it is wrong. Bitcoin difficulty does not change at midnight. It changes at a block height, every 2,016 blocks, and that block lands whenever it lands. So roughly 24 days a year a single calendar day runs partly under one difficulty and partly under the next, and a daily-grain fact silently prices the whole 24 hours at one of them.

This is not a theoretical objection. Here is the query, run against the live warehouse, comparing the correct epoch-split figures for 9 August 2026 against what a daily-grain model would have recorded:

-- correct: the day split into its two difficulty-epoch segments
-- naive:   all 24 hours priced at whichever epoch was live at 23:59 UTC
WITH correct AS (
  SELECT SUM(btc_mined_qty) AS btc, SUM(gross_revenue_usd_amt) AS usd
  FROM mining_dw.fct_fleet_mining_day WHERE date_key = 20260809
),
closing_rate AS (
  SELECT btc_mined_qty / hours_in_segment_qty AS btc_per_hr
  FROM mining_dw.fct_fleet_mining_day
  WHERE date_key = 20260809 AND epoch_key = 477   -- the epoch live at 23:59
)
SELECT c.btc AS correct_btc,
       r.btc_per_hr * 24 AS naive_btc,
       ((r.btc_per_hr * 24) / c.btc - 1) * 100 AS pct_overstated
FROM correct c CROSS JOIN closing_rate r;

Why a one percent error is worth a grain change

Because it does not cancel. If the error were random it would wash out over a year and I would leave it. Difficulty retargets have historically risen more often than they have fallen, so the error carries a sign, and a signed error compounds through every downstream number: payback date, break-even, resale timing, the lot. On a backtest it pushed projected payback about two weeks long.

The fix was a grain change, which is the expensive kind. The composite primary key gained epoch_key, and every row gained hours_in_segment_qty, which sums to exactly 24 per deployment-day and is the weight in every weighted average in the warehouse. DQ-03 fails the build if it ever does not.

04

The SQL, and the standards it obeys

Objects as they exist in the database. Not pseudocode.

Naming grammar, enforced not documented

SuffixMeansRule
_keysurrogate keyinteger, meaningless, ours. Joins use these and only these.
_idnatural or business keycomes from the source system. Never used as a join key.
_qtyadditive quantitysafe to SUM at any level.
_amtadditive moneycurrency named in the column: _usd_amt.
_cntsemi-additive countadditive across some dimensions, never across time. Roll up with LAST.
_flagbooleanNOT NULL with a default. A three-state boolean is a bug.
_ts_utctimestampalways UTC, always says so. This is not negotiable in a domain where the business day is defined by block height.

Units live in the column name. Not in a data dictionary, not in a comment. nameplate_power_w is watts. It is never kilowatts, and there is never a second column that is. This project has three power units in play, watts and kilowatt-hours and joules per terahash, and a units error between them is the single easiest way to be confidently wrong by a factor of a thousand.

Constraints that encode the business rule

-- consensus says an epoch is exactly 2016 blocks. The database says it too.
CONSTRAINT ck_epoch_2016
  CHECK (end_block_height = start_block_height + 2015),

-- consensus clamps a retarget to a factor of 4 in either direction.
-- a value outside this is a corrupt read or testnet data leaking into mainnet.
CONSTRAINT ck_retarget_clamp
  CHECK (retarget_pct_chg IS NULL OR retarget_pct_chg BETWEEN -75.0 AND 300.0),

-- a hosting contract must actually carry the fields its pricing model implies.
-- this one has caught more real mistakes than any other constraint here.
CONSTRAINT ck_pricing_coherent CHECK (
     (pricing_model_code = 'flat_all_in'           AND base_rate_usd_per_kwh IS NOT NULL)
  OR (pricing_model_code = 'revenue_share'         AND revenue_share_pct IS NOT NULL)
  OR (pricing_model_code = 'per_machine_month'     AND per_machine_month_usd_amt IS NOT NULL)
  OR (pricing_model_code = 'passthrough_plus_mgmt' AND base_rate_usd_per_kwh IS NOT NULL
                                                AND mgmt_fee_usd_per_kwh  IS NOT NULL)
  OR (pricing_model_code = 'hybrid')
),

-- accumulating snapshot milestones must be monotonic.
CONSTRAINT ck_milestone_order CHECK (
      (first_btc_date_key    IS NULL OR energised_date_key IS NULL OR first_btc_date_key    >= energised_date_key)
  AND (full_payback_date_key IS NULL OR opex_breakeven_date_key IS NULL OR
       full_payback_date_key >= opex_breakeven_date_key)
)

The ratio surface

No fact table in this warehouse contains a rate, a ratio, an average or a percentage. They all live in one view. This is the rule I care most about and I only care about it because I broke it once: I stored avg_hashrate_th_s on a daily fact, somebody summed it in a dashboard, and it produced a fleet hashrate thirty times the site's physical capacity. Nobody noticed for a week, because a big number on a tile looks correct.

CREATE VIEW mining_dw.v_fleet_mining_day AS
SELECT
  f.date_key, f.epoch_key, f.fleet_deployment_key, f.scenario_key,

  -- additive: safe to SUM again upstream
  SUM(f.work_delivered_th_qty)    AS work_delivered_th_qty,
  SUM(f.energy_consumed_kwh_qty)  AS energy_consumed_kwh_qty,
  SUM(f.btc_mined_qty)            AS btc_mined_qty,

  -- semi-additive: LAST over time, never SUM
  MAX(f.machines_installed_cnt)   AS machines_installed_cnt,

  -- non-additive: ALWAYS sum of numerator over sum of denominator.
  -- never an average of averages. correct at every level of rollup
  -- by construction, which a stored average can never be.
  SUM(f.work_delivered_th_qty)
    / NULLIF(SUM(f.hours_in_segment_qty) * 3600, 0)   AS realized_hashrate_th_s,

  SUM(f.energy_consumed_kwh_qty) * 3600000
    / NULLIF(SUM(f.work_delivered_th_qty), 0)         AS realized_efficiency_j_per_th,

  SUM(f.power_cost_usd_amt + f.pool_fee_usd_amt
      + f.hosting_fee_usd_amt + f.maintenance_usd_amt)
    / NULLIF(SUM(f.btc_mined_qty), 0)               AS cash_cost_per_btc_usd
FROM mining_dw.fct_fleet_mining_day f
GROUP BY 1,2,3,4;

Data quality, as executable assertions

Run against the live warehouse on 16 August 2026. These are the actual results, not a specimen.

A governance rule that lives in a document is a suggestion. A governance rule that fails the build is a control. Three of the five below are singular business-logic tests rather than generic not-null checks, which is the distinction that matters when someone asks what you mean by data quality.

TestAssertionCheckedFailedResultThe real bug it catches
DQ-01Every difficulty epoch spans exactly 2,016 blocks20PassA missed retarget silently prices weeks of production at the wrong difficulty.
DQ-02No fact row falls outside its epoch's real UTC window160PassThe loader joined an epoch by date instead of by block height. This is the original bug, caught automatically now.
DQ-03hours_in_segment_qty sums to exactly 24.0000 per deployment-day150PassThe retarget-day split dropped or double-counted hours. This one fails the build, because every weighted average in the warehouse weights on that column.

DQ-03, in full, because it is the interesting one

WITH per_day AS (
  SELECT date_key, fleet_deployment_key, scenario_key,
         SUM(hours_in_segment_qty) AS hrs,
         COUNT(*)                  AS segments
  FROM mining_dw.fct_fleet_mining_day
  GROUP BY 1,2,3
)
SELECT * FROM per_day WHERE ABS(hrs - 24) > 0.0001;
-- must return zero rows. returned zero rows across 15 days,
-- one of which had 2 segments (15.3333 + 8.6667 = 24.0000).
Cross-implementation check

The same model is implemented twice and independently: once in JavaScript on the Desk, once as live formulas in a spreadsheet. Both produce net profit of $3,547 a month, 181 days to mine one bitcoin, capex of $96,900 and 1.5369 BTC. Agreement to the cent across two implementations is weak evidence that the arithmetic is right and strong evidence that it is at least consistent, which is more than most models can say.

06

How I decide bitcoin is undervalued

The method, the weights, the confidence rule, and why the confidence is low even though the models agree.

The answer is undervalued, roughly 15% below a modelled fair value of $73,775, at 40% confidence. The confidence number is the part worth defending, and it is low because the models agree rather than in spite of it.

Step one: group before you weight

There are eight published ways to value bitcoin against mining economics. Five of them are the same trade wearing different hats: cost of production, difficulty regression, energy value, hashprice payback and the difficulty ribbon all resolve to some function of hashrate times efficiency times power price, divided by issuance. Their pairwise historical correlation runs 0.85 to 0.98. Averaging eight raw signals hands about 70% of the weight to one underlying factor without telling you.

So they are grouped into families first, averaged within family, and only families are weighted.

FamilyWeightFair valueMethod
Cost basis39%$71,685All-in production cost. Electrical floor is hashrate × J/TH × 24 × PUE × $/kWh, divided by daily issuance; all-in divides that by the electricity share of total cost, about 0.80 in 2026.
Hashprice payback28%$79,500What price makes a new machine pay back in 24 months at $18/TH capex and 13 J/TH. Every input is a market price rather than an assumption, which makes it the most defensible of the set.
Puell multiple22%$71,778Daily issuance value against its 365-day average. Currently 0.79, inside the 0.5 to 1.0 accumulation band.
Thermocap11%$73,803Market cap over cumulative security spend. 13.6×, which is normal range and the one metric that does not say cheap.
Regimegatenot a valueHash ribbons and miner capitulation. Treated as a multiplier on confidence, never added to the fair value. Averaging a binary state flag into a set of continuous z-scores is a category error.

Step two: the uncertainty is in the inputs, not the statistics

Nobody publishes the network's true fleet-average efficiency or its true blended power price. Those two unknowns move fair value by more than any sampling error ever could, so the band comes from a 20,000-draw Monte Carlo over them rather than from a standard error: efficiency 20 ± 2.5 J/TH, blended power $0.055 ± 0.012 per kWh, electricity share of total cost 80 ± 5%, PUE 1.10 ± 0.03. That gives P10 $64,049 and P90 $84,629.

Step three: penalise agreement

This is the part most composite models get backwards. Three of the four valuation families read hashrate or difficulty as their primary input. When they agree, that is not corroboration. It is one model answering three times. So tight dispersion across correlated families reduces confidence here rather than raising it. Wide dispersion at least tells you the models are looking at different things.

On top of that sits a structural haircut for 2026 specifically. Public miners have signed more than $70 billion of AI and HPC contracts since April and are moving megawatts off bitcoin voluntarily. Falling hashrate no longer reliably means miner distress, which breaks the causal assumption underneath every hashrate-driven model at the same time. Correlated model failure is the worst case for a composite and it looks exactly like high confluence.

The families currently agree to within 4.3% and 67% of the weight sits on models that share an input. The page therefore reports 40% confidence and prints that sentence on screen rather than burying it.

07

Time, depreciation, resale, and the transfer to a food company

How time is valued

Three ways, deliberately. Nominal: cumulative cash against capex, which is the naive break-even every calculator prints. Difficulty-adjusted: the same thing with difficulty compounding every 2,016 blocks, which pushes median break-even from 628 days to 1,095. Opportunity cost: in bitcoin terms the zero line is not "capex recovered", it is parity with simply having bought the coin with the same money. That last framing is the one a mining investor actually uses and almost no calculator offers it.

Depreciation is two different things

Book value is an accounting policy: straight line over three or five years, or the MACRS five-year class which is the real US tax treatment for mining hardware. It hits earnings and tax and has no obligation to track reality.

Market value is what somebody pays. It is driven by remaining earning power, not by age, which is why an old rig goes to zero the week hashprice drops below its power cost rather than gliding politely to salvage. Three methods, shown as a range rather than a point: a cohort regression of log price-per-terahash on machine age across the catalogue, giving -20.3% per year at R² 0.57; an income approach valuing the machine at what it earns a buyer at their power rate over their required payback; and a flat schedule anchored on the one clean observation that exists, a 44.8% new-to-used discount on the same model in the same month from Luxor's RFQ fill data in August 2023.

The cohort figure carries a caveat I state on the page: it is a cross-section, not a time series, so it confounds a machine's age with the vintage of its silicon. It tells you what old machines fetch today, not what today's machines will fetch when they are old.

Resale agency

Selling used hardware costs you a cut, and the structure varies. eBay publishes 13.6% to $7,500 and 2.35% above. Compass marketplace is reported at 10% by third parties and discloses nothing itself. Luxor's trading desk is explicitly principal, not agency, meaning you face a spread rather than a commission. Kaboomracks and the consignment desks publish nothing. I could not find a single published bid-ask spread for used ASICs anywhere, and the model says so rather than inventing one.

Hosting and maintenance

The schema supports five real hosting pricing models because all five exist in the market: flat all-in per kWh (Simple Mining at $0.08 falling to $0.07 with scale, Blockware at $0.07), energy pass-through plus a management fee, revenue share (Sazmining takes 15% of BTC mined plus electricity at cost), flat per machine per month (Abundant Mines at $225, all-inclusive of repairs and insurance), and hybrid. A CHECK constraint refuses a contract row that does not carry the fields its pricing model implies.

The transfer, said plainly

Swap the nouns and this is a consumer packaged goods sales warehouse. A difficulty epoch is a trade promotion window that starts mid-day. hours_in_segment_qty is the allocation weight on a deduction split across two overlapping promotions. The stored-average bug is somebody summing average selling price across SKUs. Nine ASIC vendors quoting one machine is three freight forwarders quoting one landed cost. Five hosting pricing models is five customer trade-terms structures.

The domain is different and the failure modes are identical. That is the actual argument for hiring someone who has modelled a different industry carefully rather than the same one carelessly.

08

What I did not do, and what I would do next

A work sample that only lists strengths is a sales page. These are the things I would raise myself in the first interview, before someone else found them.

  • No orchestration. Migrations are versioned and the assertions run, but there is no scheduler, no dependency graph, no freshness SLA. In production I would want the tests running on every load and failing loudly, not run by me on demand.
  • Scenarios share tables with actuals. Every fact carries scenario_key and every view filters it. It works, and I have still watched people forget the filter and put simulated revenue in front of someone who thought it was real. A control that depends on remembering is not a control. Separate schema, separate grant, same conformed dimensions.
  • Epoch splitting happens inside the fact build. It should be its own ingest step with its own tests. Right now a late-arriving block-height correction means rebuilding a whole day's partition because one timestamp moved forty seconds.
  • Small seed. Fifteen days and sixteen fact rows. Enough to prove the grain and run the assertions, not enough to say anything about query performance at scale. I have not tested a partition strategy because there is nothing to partition yet.
  • No Snowflake or Databricks. Stated again because it is the real gap against the posting. The modelling transfers; the platform-specific work does not, and month one would be slower for it.
  • ASIC price data is asks, not fills. The best free fill source, eBay completed listings, is blocked to automated collection and would need a browser session. Everything else public is advertising.
